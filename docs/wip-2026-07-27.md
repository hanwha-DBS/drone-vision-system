### 2. 30장 분석 vs 29장 아카이브 — 버그 아님 (원인 규명 완료)

이벤트 파일 363개 세션 복원 결과, 마지막 세션(14:05:39~14:07:12, 29장)에서
`idx 301 → 394` 한 곳만 샘플링 한 주기 비어 있음. 세션 내 frame_index 중복 없음(파일명 충돌 배제).
→ **그 스냅샷에 임계값 넘는 사람·차량이 없었음.** 이벤트는 감지 시에만 저장되므로 정상.

부수적으로 발견한 진짜 결함은 수정함: `inference_worker`가 결과를 `put_latest`로 넘겨
결과 큐가 차면 **분석은 됐는데 이벤트가 조용히 사라짐**. 파일 재생은 `put_blocking`으로 변경.

## 방금 한 변경 — **미검증, 여기서 이어서 시작**

### A. 샘플 수 감소 (30장 → 21장) 수정

원인: `put_blocking`을 결과 큐에 적용하면서 역압이 샘플러까지 전파.
`snapshot_scheduler`가 큐 대기 후 `next_sample_at = now + interval`로 **재앵커**해서
대기 시간이 매 간격에 가산됨.

```python
# engine.py  snapshot_scheduler (파일 재생 분기)
next_sample_at = max(next_sample_at, time.perf_counter())   # 변경 후
```

**→ 실제로 30장 수준으로 돌아오는지 확인 필요.**

### B. 칸이 압축되지 않고 가로로 계속 늘어나도록

- `.gauge-cell`: `flex: 0 1 32px` → **`flex: 0 0 var(--gauge-cell-w, 32px)`** (shrink 완전 제거)
- 두 트랙을 **하나의 스크롤 컨테이너** `#gaugeScroll`에 넣음 (행 정렬 어긋남 방지)
- 그리드: `auto minmax(0, max-content) auto` — 칸이 쌓이면 트랙이 자라며 텍스트를 밀어내고,
  가용 폭에 닿으면 압축 대신 가로 스크롤
- 새 칸 생기면 자동으로 오른쪽 끝 추적 (사용자가 왼쪽으로 스크롤해 둔 경우 제외)
- `GAUGE_MAX_CELLS` 150 → 600
- 마크업 구조 변경: `.gauge-names` / `#gaugeScroll` / `.gauge-values` 3열

**→ 렌더링 확인 안 함. `npm start` 필요.**
